# M3. 프로젝트와 티켓

상태 (2026-10-13): **1단계 구현됨. 2·3단계는 핵심이 구현됨**(티켓 만들기·목록·상세, 문서 편집기, 프리셋 목차). 4단계는 **댓글과 `@` 태그가 구현됨**(D-101), 변경 이력은 활동 기록(D-061)까지이고 본문의 이전 판 보기는 없다.

구현된 것과 아직 아닌 것은 아래 "지금 구현된 범위"가 기준이다. 그 아래 2~4단계의 글은 처음 쓴 명세이고, 구현하면서 달라진 점은 "지금 구현된 범위"에 적었다.

## 지금 구현된 범위

### 독립 티켓 (D-062): 아래 내용이 이 문서의 다른 설명보다 우선한다

티켓은 **프로젝트에 속하지 않고 워크스페이스에 있다.** 프로젝트는 티켓이 "연결"되는 대상일 뿐이다 (Linear 에서 티켓이 팀에 속하고 프로젝트는 연결인 것과 같다. Flowbit 에는 팀이 없어 워크스페이스 전체가 팀 하나다).

- **키와 번호**: `<워크스페이스 티켓 키>-<번호>`(기본 `FB-12`). 번호는 워크스페이스 전체의 일련번호다. 티켓 키는 관리자 설정의 워크스페이스에서 바꾼다(모든 티켓의 키가 바뀌고 번호는 그대로). 프로젝트 연결을 바꿔도 키는 그대로다.
- **권한**: 프로젝트에 연결된 티켓은 그 프로젝트를 따른다(구성원만 보고, 보기 역할은 고치지 못한다). **어디에도 연결되지 않은 티켓은 로그인한 누구나 보고 고친다.** 볼 수 없는 티켓은 404.
- **화면에서 알려 주기** (2026-10-13): 티켓의 속성 칸(새 티켓 창과 상세가 같이 쓴다)에서 프로젝트가 "프로젝트 없음"이면 그 아래에 "프로젝트는 고르지 않아도 됩니다. 고르지 않은 티켓은 구성원 누구나 보고 수정할 수 있습니다."를 보여 준다(`messages.issues.noProjectHint`). 온보딩 투어의 전체 티켓·속성 단계도 같은 내용을 말한다.
- **새 티켓은 어디서나** (D-123): 사이드바 맨 위에 "새 티켓" 버튼(좁은 화면은 위쪽 줄의 `+`)이 있고, 목록이 없는 화면에서도 `C` 가 된다(`features/issues/components/new-issue-launcher.tsx`). 프로젝트 화면에서 열면 그 프로젝트가 골라져 있다(편집 권한이 있을 때). **"새 티켓" 버튼은 사이드바에만 있다**(목록 위의 버튼은 없앴다. 티켓이 하나도 없는 빈 화면에만 다음 행동으로 남아 있다). 티켓 목록이 있는 화면에서는 사이드바 버튼과 `C` 가 그 목록의 창을 연다(그 프로젝트를 이어받는다). **새 티켓의 담당자는 "담당자 없음"으로 시작한다. 단 "내 티켓"(두 탭 모두)에서 사이드바 버튼이나 `C` 로 연 창은 요청한 나를 담당자로 미리 골라 둔다**(D-195. D-123 ① 을 바꾼다. 바꾸거나 지울 수 있고, 창에서 프로젝트를 바꾸면 다른 담당자는 비워지지만(D-125) 나는 지우지 않은 한 그대로 남는다(편집 역할이 있는 프로젝트에만 티켓을 만들 수 있어 나는 늘 담당자가 될 수 있다). "계속 만들기"와 만든 뒤에도 나로 돌아온다. 삭제된 티켓을 보는 중인 "내 티켓"은 목록이 읽기 전용이라 사이드바 버튼이 공용 창을 열고, 거기서는 담당자가 비어 있다). 구현했지만 화면은 확인하지 않았다.
- **목록의 묶음과 기억** (D-130, 2026-10-15): 목록 보기의 도구 줄에 "묶음" 메뉴(상태별·우선순위별·담당자별·프로젝트별·묶지 않음, `?group=`, 프로젝트별은 여러 프로젝트를 보는 목록에만)와 "완료된 티켓" 메뉴(완료: 최근 2주·최근 1개월·전체·숨김, `?completed=`, 기본 2주)가 있다. 완료·취소 티켓은 끝난 지(`completedAt`: 마지막 상태 변경) 그 기간이 지나면 줄에서 빠지고, 그 묶음 끝에 "완료된 티켓 N개 더 보기"가 나온다(누르면 "전체"). 담당자가 여럿인 티켓은 담당자별 묶음에서 사람마다 나온다. **내 티켓·전체 티켓·프로젝트의 티켓은 상태·우선순위·담당자·라벨 필터, 정렬, 묶음, 완료 기간을 함께 기억한다**(이 브라우저, `features/issues/list-memory.ts`): 주소가 비어 있는 목록을 열면 마지막으로 쓴 값이 들어가고, 바꿀 때마다 저장된다. 프로젝트 필터와 검색어는 기억하지 않는다. 링크로 값이 있는 주소를 열면 그 값을 따른다.
- **목록의 정렬** (D-124): 목록 보기의 도구 줄에 "정렬" 메뉴가 있다: 최근 만든 순(기본), 최근 수정한 순, 우선순위 높은 순, 기한 빠른 순(기한 없는 것은 뒤), 제목순. 상태별 묶음은 그대로이고 묶음 안의 순서만 바뀐다. 하위 티켓은 상위 티켓 아래에 만든 순서로 남는다. 고른 값은 주소에 둔다(`?sort=priority`, 기본값은 뺀다). 타임라인과 캘린더에는 없다(`features/issues/sort.ts`).
- **목록의 프로젝트 칸** (D-123): 전체 티켓·내 티켓 목록은 768px 부터 프로젝트 칸을 보이고, 연결하지 않은 티켓은 흐린 글씨로 "프로젝트 없음"이라고 쓴다.
- **프로젝트 개요의 티켓 요약** (D-123): 설명 아래 "티켓" 구역에 진행 막대(`n건 중 m건 완료`, 취소는 세지 않는다)와 상태별 건수가 있다. 상태를 누르면 그 상태로 거른 프로젝트의 티켓 목록이 열린다(`project-issue-summary.tsx`).
- **프로젝트 개요에 내 역할을 따로 쓰지 않는다** (2026-10-13, 사용자 지정): 구성원 카드에서 내 줄에 "나" 표시가 붙는다.
- ~~**완료된 목표와 목표 줄** (D-136, D-163)~~: **목표(마일스톤) 기능은 없앴다(D-189).**
- **프로젝트에 "티켓" 탭이 없다** (2026-10-15, 사용자 지정, D-135): 프로젝트의 티켓은 전체 티켓을 그 프로젝트로 거른 목록(`/issues?project=`)이다. 개요의 "모두 보기"·상태별 건수, 그 프로젝트로 거른 목록 링크가 그리로 간다. 예전 주소 `/project/{id}/issues` 는 같은 필터로 넘겨 준다(`next.config.ts` 의 `redirects()`, 서버가 페이지를 그리기 전에 307 으로 답한다: 전에는 페이지가 `redirect()` 했는데, 그러면 프로젝트의 머리글이 먼저 그려지고 그 안의 "보는 사람" 요청이 이동에 끊겨 E2E 의 `settled()` 가 그 요청을 기다렸다). 아래 글에서 "프로젝트의 티켓(목록)"은 이 거른 목록을 말한다.
- **프로젝트의 "한 줄 요약"이 없다** (2026-10-15, 사용자 지정, D-134): 개요의 요약 입력칸과 새 프로젝트 창의 "한 줄 요약" 칸을 없앴다. 프로젝트를 설명하는 것은 개요의 설명 문서 하나다. `projects.description` 컬럼과 API 필드는 남아 있지만 화면은 쓰지 않는다.
- **개요 본문에 구성원 수·만든 날짜 줄을 두지 않는다** (2026-10-15, 사용자 지정): 오른쪽 "속성" 카드의 "구성원"·"만든 날" 줄과 겹쳐서 한 줄 요약 아래의 것을 없앴다. 두 값은 속성 카드에만 있다.
- **개요의 구성원 카드는 보여 주기만 한다** (2026-10-15, 사용자 지정): 사람(아바타·이름·아이디)과 내 줄의 "나"뿐이다. 역할(관리·편집·보기)을 쓰지 않고, 추가 "+"·제거 "×" 도 없다. 추가·제거·역할 변경은 프로젝트 설정(`/project/{id}/settings`)에서만 한다. 설정의 "프로젝트 구성원"에는 **추가 줄(추가할 사람·역할·추가)이 늘 있다**: 모든 사람이 이미 구성원이면 사람 칸이 비활성으로 "모든 구성원이 이미 이 프로젝트에 있습니다"라고 말한다(사용자 지정 2026-10-21: 칸이 사라져 기능이 없어진 줄 알았다). 아래 표의 "구성원 역할 변경·추가 버튼·제거 버튼" 중 개요에 있던 것은 없어졌다.
- ~~**고르지 않은 목표는 빈칸으로 보인다**~~: 목표와 함께 없앴다(D-189).
- **연결 바꾸기**: 티켓 상세 오른쪽 "프로젝트"에서 프로젝트를 고른다. 연결하려면 그 프로젝트에서 편집 권한이 있어야 한다. 담당자는 연결된 프로젝트의 구성원 중에서(독립 티켓은 모든 구성원 중에서) 고른다.
- **프로젝트에는 키가 없다** (D-082). 프로젝트는 내부 ID 로만 가리킨다: 주소 `/project/{id}`, API `/api/v1/projects/{id}`, 실시간 주제 `project:{id}`. 화면에는 이름만 보인다. 이름은 겹쳐도 된다.
- **주소**: `/issue/FB-12`(번호만 읽는다). 앱 안에서 티켓을 누르면 어느 화면에서든 그 위에 대화상자로 뜬다. **주소를 직접 열거나 새로 고쳐도 대화상자다** (D-074): 뒤에 둘 화면이 없으므로 전체 티켓 목록 위에 뜨고, 닫으면 `/issues` 로 간다. `/issues` 는 볼 수 있는 모든 티켓("전체 티켓"), `/project/{id}/issues` 는 그 프로젝트에 연결된 티켓, `/my-issues` 는 내 티켓.
- **API**: `GET/POST /api/v1/issues`(`?project={id}` 로 좁히기, 만들 때 `projectId`·`parentId`·`customProperties`(D-193, [custom-properties.md](custom-properties.md))), `GET/PATCH /api/v1/issues/{번호}`(`projectId`, `parentId` 를 `null` 로 보내면 떼어 낸다), `…/activity`, `…/subscription`, `…/reactions`, `…/attachments`, `…/documents`. `GET/POST /api/v1/projects/{id}/issues` 는 그 프로젝트의 목록과 "그 프로젝트에 연결해 만들기"로 남아 있다. 한 건 조회 응답에는 `canEdit`, `canAddSubIssue`, `subIssues`, `reactions`, `attachments`, `documents` 가 더 들어 있다.

- 본문 변경의 이전 판 보기 (지금은 만들지 않기로 했다, D-225)

구현하면서 명세와 달라진 점:

- 상태는 프로젝트별 표가 아니라 **고정된 5개 값**이다(`BACKLOG`, `READY`, `IN_PROGRESS`, `DONE`, `CANCELED`). 프로젝트마다 상태를 바꾸는 기능을 만들 때 표로 옮긴다.
- 프리셋은 표가 아니라 티켓의 값(`BUG`, `ENHANCEMENT`, `FEATURE`)이고, 목차는 프런트엔드가 가진다.
- 티켓 본문은 `issues.content`(jsonb), 거기서 뽑은 글자는 `issues.description`(text)에 둔다. 프로젝트는 `description` 이 한 줄 요약, `content` 가 설명 문서다.
- 프로젝트 요약과 설명은 **편집 역할부터** 고칠 수 있다. 이름 변경만 관리 역할이 필요하다.

티켓 API (모두 프로젝트 구성원만, 쓰기는 편집 역할부터):

| 메서드와 경로 | 설명 |
|---|---|
| `GET /api/v1/projects/{id}/issues` | 목록. 최근에 만든 것부터. `content` 는 빠진다 |
| `POST /api/v1/projects/{id}/issues` | `{ title, content?, preset?, status?, priority?, assigneeIds?, dueDate? }` → 201. 제목만 필수. `assigneeIds` 는 사람 id 목록(D-125) |
| `GET /api/v1/projects/{id}/issues/{number}` | 한 건. `content` 포함 |
| `PATCH /api/v1/projects/{id}/issues/{number}` | 보낸 항목만 바뀐다. `dueDate`, `preset`, `content` 는 `null` 로 지운다. `assigneeIds` 는 담당자 전체를 바꾸고 `[]` 이면 모두 뺀다(D-125). 응답의 담당자는 `assignees`(배열, 지정한 순서) |
| `PATCH /api/v1/projects/{id}` | `{ name?, description?, content?, status?, priority?, leadId?, startDate?, targetDate?, labels? }`. `content` 는 개요 문서. `leadId`, `startDate`, `targetDate` 는 `null` 로 지운다 |

### 프로젝트 업데이트와 건강도

사용자가 Linear 의 Health 열("On track · 1h")을 지정했다 (D-048). 건강도는 따로 고르는 속성이 아니라 **가장 최근 프로젝트 업데이트의 값**이다.

- 업데이트: 건강도(순조로움 `ON_TRACK` / 위험 `AT_RISK` / 지연 `OFF_TRACK`) + 글(선택, 5000자 이하, 평문). 편집 역할부터 남긴다. **쓴 사람(편집 역할 이상일 때)과 관리 역할은 지울 수 있다**(D-085; 지우면 건강도는 그 앞의 업데이트 값으로 돌아간다). 고치는 기능은 없다. 글이 없고 건강도도 직전 업데이트와 같으면 새로 알릴 것이 없으므로 화면이 "업데이트 남기기"를 막는다(API 는 받는다).
- 화면: 프로젝트 개요의 마일스톤 아래 "프로젝트 업데이트"(건강도 칩 + 글 + "업데이트 남기기", `Ctrl/⌘+Enter`; 최근 것부터 50개). 속성 카드의 "건강도" 줄, 전체 프로젝트 표의 "건강도" 열(`순조로움 · 1시간 전`). 업데이트가 없으면 "업데이트 없음".
- 남기면 실시간으로 `project:{id}` 를 알린다.

| 메서드와 경로 | 설명 |
|---|---|
| `GET /api/v1/projects/{id}/updates` | 최근 것부터 50개: `[{ id, health, body, author, createdAt }]` |
| `POST /api/v1/projects/{id}/updates` | `{ health, body? }` → 201. 편집 역할부터 |
| `DELETE /api/v1/projects/{id}/updates/{updateId}` | 204. 쓴 사람(편집 역할 이상) 또는 관리 역할. 그 밖에는 403, 없는 업데이트는 404 `PROJECT_UPDATE_NOT_FOUND` |

### ~~마일스톤 (화면 이름은 "목표")~~ — 없앴다 (D-189)

프로젝트 안의 단계를 나누던 **목표(마일스톤)는 없앴다**(2026-10-23, 사용자 지시). 단계는 상위 티켓과 하위 티켓으로 나눈다. 마이그레이션(`V4__remove_milestones.sql`, 지금은 `V1` 에 합쳐졌다: D-191)이 `milestones`·`milestone_assignees` 표, `issues.milestone_id`, 목표의 댓글·활동·속성, 티켓 활동의 `MILESTONE_CHANGED` 를 지운다(티켓은 남는다). API `…/milestones`, 티켓의 `milestoneId`·`milestone`, 프로젝트의 `currentMilestone`, 검색의 `milestones`, 프레즌스 키 `milestone:` 도 없다. 옛 결정(D-045, D-057, D-113 …)은 기록으로만 남는다.

### 프로젝트 속성

사용자가 Linear 의 프로젝트 화면을 보여 주며 지정했다 (D-042). 개요 오른쪽 "속성" 카드에서 그 자리에서 바꾸고, **편집 역할부터** 바꿀 수 있다.

| 속성 | 값 | 기본 |
|---|---|---|
| 상태 `status` | 백로그 `BACKLOG` / 계획됨 `PLANNED` / 진행 중 `IN_PROGRESS` / 완료 `COMPLETED` / 취소 `CANCELED` (고정 5개) | 백로그 |
| 우선순위 `priority` | 티켓과 같은 값: 없음 / 긴급 / 높음 / 보통 / 낮음 | 없음 |
| 리드 `lead` | 프로젝트의 활성 구성원 한 명 또는 없음. 아니면 422 `NOT_A_MEMBER`(필드 `leadId`) | 없음 |
| 기간 `startDate` → `targetDate` | 날짜 두 개, 각각 비울 수 있다. 시작일이 종료일보다 늦으면 422 `BEFORE_START`(필드 `targetDate`) | 없음 |
| 라벨 `labels` | 자유 입력 태그. 1~30자, 최대 10개, 대소문자 무시하고 중복 제거. 입력할 때 다른 프로젝트에 쓰인 라벨을 제안한다 | 없음 |

- 라벨은 아직 별도 표(색, 관리 화면)가 없다. 프로젝트의 `labels` 배열에 이름만 둔다. 라벨 관리가 필요해지면 표로 옮긴다.
- 프로젝트 목록 API(`GET /api/v1/projects`)에도 이 속성들이 함께 온다. 목록 화면에 보여 주는 것은 아직 없다.

- 담당자는 그 프로젝트의 활성 구성원이어야 한다 (422 `NOT_A_MEMBER`, 필드 `assigneeIds`). 10명을 넘으면 422 `TOO_MANY` (D-125).
- 문서(`content`)는 서버가 검증한다: 편집기가 제공하는 블록과 서식만 허용하고, 링크는 `http(s)`, `mailto`, 앱 안의 경로만 받는다. 이미지 주소는 이 서버가 저장한 파일(`/api/v1/files/<key>.webp`)만, 임베드는 Figma·Google·Office·Outline 의 정해진 주소만(D-139), 표 칸의 정렬은 정해진 값(`left/center/right`, `top/middle/bottom`)만, 칸 합치기 수는 1~100만 받는다. 어기면 422 `INVALID_DOCUMENT`. HTML 은 저장하지도 내보내지도 않는다.
- 티켓 번호는 프로젝트별로 1부터 차례로 붙고, 동시에 만들어도 겹치지 않는다.

백엔드 테스트: `IssuesIntegrationTest`(댓글 3개 포함), `RichTextIntegrationTest`(7개), `NotificationsIntegrationTest`(태그 알림 1개).

사용자가 정한 것 (D-032):

- 프로젝트를 만들면 권한이 있는 사용자가 들어와 티켓·고도화 같은 글을 등록하고 정리한다.
- Jira처럼 **프리셋**(정해진 항목)을 먼저 채우고, Outline처럼 **문서**로 세부 내용을 적는다. 개발자는 이 글을 보고 개발한다.
- **팀 개념은 없앤다.** 프로젝트가 티켓의 집이자 권한 단위다.
- 프리셋은 기본 3종을 제공하고 관리자는 목차 문구만 고친다.
- 구성원 추가를 이번 범위에 넣는다.

그 밖의 세부(권한 단계, 상태 목록, 편집기, 화면 구성)는 에이전트의 제안이다. 각 단계를 구현하기 전에 "확인이 필요한 것"을 사용자에게 확인한다.

## 한눈에 보기

```
워크스페이스
 ├─ 구성원 (관리자 / 구성원)
 └─ 프로젝트 FLOW  ── 프로젝트 구성원 (관리 / 편집 / 보기)
      ├─ 상태 목록 (백로그 → 준비됨 → 진행 중 → 완료, 취소)
      ├─ 프리셋 (버그, 고도화, 기능 요청)
      └─ 티켓 FLOW-12
           ├─ 속성: 상태, 담당자, 우선순위, 기한, 라벨      ← 프리셋과 무관하게 모두 같다
           ├─ 문서: 프리셋이 깔아 준 목차 + 자유로운 본문    ← Outline 같은 부분
           └─ 댓글, 변경 이력
```

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | 구성원 추가·관리, 프로젝트 만들기, 프로젝트 권한 | **구현됨** |
| 2 | 프리셋 3종, 티켓 쓰기(속성 + 문서 + 자동 목차) | 명세만 |
| 3 | 티켓 목록(상태별 묶음, 필터), 상태 변경, 실시간 반영 | 명세만 |
| 4 | 댓글, 변경 이력 | 댓글·`@` 태그·활동 기록 구현 ("지금 구현된 범위") |

## 용어

| 용어 | 코드 | 뜻 |
|---|---|---|
| 구성원 | `user` | 워크스페이스에 로그인하는 사람. 워크스페이스 역할은 관리자(`ADMIN`) / 구성원(`MEMBER`) |
| 프로젝트 | `project` | 티켓의 집이자 권한 단위. 키(`FLOW`)를 가진다 |
| 프로젝트 구성원 | `projectMember` | 프로젝트에 들어올 수 있는 사람과 그 역할 |
| 티켓 | `issue` | 프로젝트에 등록하는 글 하나. 버그든 고도화든 기능 요청이든 모두 티켓이다. 키는 `FLOW-12` |
| 프리셋 | `preset` | 티켓의 종류. 새 티켓의 문서에 깔리는 목차를 정한다 |

## 권한

워크스페이스 역할과 프로젝트 역할, 두 겹이다.

| 할 수 있는 일 | 프로젝트 밖 구성원 | 보기 `VIEWER` | 편집 `EDITOR` | 관리 `MANAGER` | 워크스페이스 관리자 |
|---|---|---|---|---|---|
| 전체 프로젝트 목록에서 보기(이름, 속성, 건강도, 진행률) | ○ (D-047) | ○ | ○ | ○ | ○ |
| 프로젝트에 들어가기 | ✕ ("권한 없음" 화면, 접근 요청) | ○ | ○ | ○ | 구성원인 프로젝트만 (D-131) |
| 티켓 읽기, 댓글 읽기 | ✕ | ○ | ○ | ○ | ○ |
| 티켓 쓰기·고치기, 댓글 쓰기 | ✕ | ✕ | ○ | ○ | ○ |
| 프로젝트 이름·설명, 프리셋 목차 고치기 | ✕ | ✕ | ✕ | ○ | ○ |
| 프로젝트 구성원 추가·역할 변경·내보내기 | ✕ | ✕ | ✕ | ○ | ○ |
| 프로젝트 만들기 | ○ (만든 사람이 관리 역할) | | | | ○ |
| 워크스페이스 구성원 추가·역할 변경·비활성화 | ✕ | | | | ○ |

- **모든 프로젝트가 전체 프로젝트 목록에 보인다** (D-047, 사용자 지정). 들어갈 수 없는 프로젝트는 자물쇠가 붙고, 누르면 `/no-access/{id}` 에서 "권한이 없습니다"와 그 프로젝트의 관리 역할(이름·아이디·사진)을 보여 준다. **"접근 요청" 버튼**으로 관리 역할에게 요청을 보낸다(D-128, 아래 "접근 요청"). 사이드바 "내 프로젝트"에는 **들어갈 수 있는 프로젝트**(직접 구성원으로 추가된 것과 "모든 구성원에게 열린" 것, 곧 `myRole` 이 있는 것)가 있다. 프로젝트 응답의 `member` 는 직접 구성원인지만 말한다(D-192).
- 목록 밖의 데이터(개요, 티켓, 구성원, 마일스톤, 업데이트)는 지금처럼 구성원이 아니면 404 로 답한다. 화면은 `GET /api/v1/projects/{id}/access`(로그인한 누구나: `{ id, name, myRole, managers, requestedAt }`)로 "없는 프로젝트"와 "권한 없음"을 가른다.

#### 접근 요청 (D-128, 2026-10-15)

- **요청**: "권한 없음" 화면의 "접근 요청" 버튼. 누르면 "요청했습니다" 상태가 되고, 다시 들어와도 "요청함 · 날짜"로 보인다(`requestedAt`). `POST /api/v1/projects/{id}/access-requests` → 프로젝트 들어가기 응답(`/access` 와 같은 모양). 이미 구성원이면 409 `ALREADY_MEMBER`. 이미 대기 중이면 그대로 두고 알림도 다시 보내지 않는다.
- **알림**: 그 프로젝트의 활성 관리 역할에게(없으면 워크스페이스 관리자에게) 메일·푸시·API 알림으로 바로 간다(모으지 않는다). 제목 `[프로젝트 이름] 접근 요청`, 머리말 `김지민 님이 프로젝트 접근을 요청했습니다`, 링크 `/project/{id}/settings#access-requests`. API 알림은 `event: project.access_requested`, `issue: null`, `project: { id, name, url }`, `changes: [{ type: "ACCESS_REQUESTED", detail: { project } }]`([M7a](M7a-notification-channels.md)).
- **승인·거절**: 프로젝트 설정의 "구성원" 맨 아래 **"승인 대기"**(관리 역할에게만, 요청이 있을 때만). 사람마다 역할(관리·편집·보기, 기본 편집)을 고르고 "승인" 또는 "거절". 승인하면 그 역할의 구성원이 되고 요청은 지워진다. 거절하면 요청만 지워진다(다시 요청할 수 있다). 관리 역할이 위의 "추가"로 그 사람을 넣어도 요청은 지워진다.
  - `GET /api/v1/projects/{id}/access-requests`(관리 역할): `[{ userId, loginId, displayName, avatarUrl, requestedAt }]`, 오래된 요청부터.
  - `POST …/access-requests/{userId}/approve` `{ role }` → 구성원 목록. `DELETE …/access-requests/{userId}` → 204. 요청이 없으면 404 `ACCESS_REQUEST_NOT_FOUND`.
- 요청한 사람에게 결과를 알리지는 않는다.
- **워크스페이스 관리자도 구성원으로 추가된 프로젝트에만 들어간다** (D-131, 2026-10-15). 다른 프로젝트는 일반 구성원과 같이 "권한 없음" 화면이다. 관리자 설정 > 구성원의 "프로젝트 권한"에서는 모든 프로젝트의 역할을 정할 수 있다(`PUT/DELETE /api/v1/admin/members/{id}/projects/{projectId}`). **프로젝트의 "설정" 탭은 그 프로젝트의 관리 역할에게만 보이고**, 다른 사람이 설정 주소를 열면 개요로 간다.
- 프로젝트에는 관리 역할이 항상 한 명 이상 있어야 한다. 마지막 관리 역할을 내보내거나 낮출 수 없다 (409 `LAST_MANAGER`). **비활성화된 사람은 세지 않는다**: 로그인할 수 있는 관리 역할이 한 명뿐이면 그 사람이 마지막이다 (D-173).
- **비활성화된 사람은 프로젝트 구성원 목록에 나오지 않는다** (D-173, 사용자 지정 2026-10-22). `GET /api/v1/projects/{id}/members`(프로젝트 개요의 구성원 카드, 설정의 "프로젝트 구성원", 담당자·`@` 태그 후보)와 프로젝트 요약의 `memberCount`, 권한 없음 화면의 관리 역할 목록이 같은 규칙이다. 구성원 자격(`project_members` 행)은 그대로라서 다시 활성화하면 돌아온다. 이미 그 사람이 담당자인 티켓에는 계속 보인다.
- **프로젝트 권한을 주면 바로 들어갈 수 있다** (D-173): 관리자 설정 > 구성원의 "프로젝트 권한"에서 역할을 고른 직후 그 화면이 서버 화면(사이드바, 전체 프로젝트, 프로젝트 페이지)을 새로 읽는다. 자기 변경의 실시간 알림은 건너뛰기 때문이다. `/no-access/{id}` 화면은 열려 있는 동안·다시 보일 때·창으로 돌아올 때 권한을 다시 확인하고, 생겼으면 프로젝트로 보낸다(`AccessWatcher`).
- 관리자는 자기 자신의 워크스페이스 역할을 바꾸거나 자신을 비활성화할 수 없다 (409 `CANNOT_CHANGE_SELF`). 그래서 관리자가 한 명도 없는 상태가 생기지 않는다.
- 판단은 항상 백엔드가 한다. 화면에서 버튼을 숨기는 것은 편의다.

#### 모든 구성원에게 열기 (D-192, 2026-10-23)

- **프로젝트 설정 > "공개 범위"**(관리 역할에게만)에서 "지정한 구성원만"(기본) 또는 "모든 구성원에게 열기"를 고른다. 새 프로젝트 창에서도 고를 수 있다. API 는 `PATCH /api/v1/projects/{id}` 의 `{ openToAll: boolean }`(관리), `POST /api/v1/projects` 의 `{ openToAll? }`. 프로젝트 응답에 `openToAll` 이 온다.
- **열려 있으면 로그인할 수 있는(활성) 모든 구성원이 그 프로젝트에 편집 역할로 들어간다**: 티켓 읽기·쓰기·고치기·댓글, 프로젝트 개요·문서·속성 고치기. 이름·공개 범위·구성원·Git 저장소·아이콘·보관은 관리 역할만. 직접 구성원의 역할이 관리면 그대로이고, 보기 역할인 사람도 열려 있는 동안은 편집이다.
- **회원가입과 상관없이 같은 규칙이다**: 관리자가 계정을 만들거나 LDAP·SSO 로 처음 로그인해 가입한 사람은, 구성원 행을 만들지 않아도 활성인 순간부터 열린 프로젝트 전부에 들어간다. 프로젝트를 다시 닫으면 직접 구성원만 남는다.
- 열린 프로젝트의 **사람 목록**(`GET …/members`: 담당자·`@` 후보, 개요의 구성원 카드)과 `memberCount` 는 활성 구성원 전체다. 응답의 `direct` 가 거짓이면 직접 추가된 사람이 아니다. 설정의 "프로젝트 구성원"은 `direct` 인 사람만 보여 역할을 정한다(관리 역할을 따로 지정해 두는 곳이다. 직접 관리 역할이 한 명 이상 있어야 하는 규칙은 그대로).
- **개요 화면**: 열린 프로젝트에는 오른쪽의 "구성원" 카드를 그리지 않는다. "속성" 카드의 "구성원 N명" 줄이 "공개 범위 · 공개 프로젝트"(지구 아이콘)로 바뀐다. 사람을 고르는 칸(리드·담당자·`@`)은 그대로 활성 구성원 전체를 보인다.
- 열면 대기 중이던 접근 요청은 지워진다. 열린 프로젝트에는 "권한 없음" 화면이 없고 접근 요청은 409 `ALREADY_MEMBER` 다. 검색·티켓 목록·보는 사람·알림 받는 사람(프로젝트 구독자)도 같은 규칙을 따른다.
- 바꾸면 프로젝트 활동에 `ACCESS_CHANGED`(`{ open }`, 알림은 없음), 감사 로그 `PROJECT_ACCESS_CHANGED`. 관리자 설정 > 구성원 > "프로젝트 권한"에는 열린 프로젝트가 "모든 구성원에게 열림"으로 보인다(역할이 비어 있어도 들어갈 수 있다. `GET /api/v1/admin/members/{id}/projects` 의 `openToAll`).

## 1단계: 구성원과 프로젝트 (구현됨)

### 구성원 관리 (워크스페이스 관리자)

- 관리자가 구성원을 **직접 만든다**: 아이디, 임시 비밀번호, 이름(선택), 역할. 이메일 초대는 없다(이메일 발송 기능이 없다). 관리자가 아이디와 비밀번호를 당사자에게 전달한다.
- 아이디와 비밀번호 규칙은 초기 설정과 같다 ([M1-auth-and-setup.md](M1-auth-and-setup.md)).
- 역할 변경, 비활성화/다시 활성화, 비밀번호 재설정.
- 비활성화하거나 비밀번호를 재설정하면 그 사람의 로그인 세션이 모두 끝난다.
- 구성원을 삭제하는 기능은 없다. 비활성화만 한다(쓴 글과 이력이 남아야 한다).
- 감사 로그: `MEMBER_CREATED`, `MEMBER_ROLE_CHANGED`, `MEMBER_DISABLED`, `MEMBER_ENABLED`, `MEMBER_PASSWORD_RESET`.
- **화면은 왼쪽에 사람 목록, 오른쪽에 고른 사람의 설정이다** (`/admin/members`, 사용자 지정 2026-10-13: 한 줄에 사람과 버튼을 다 늘어놓은 예전 목록이 조잡했다). 왼쪽: 검색(이름·아이디·이메일), 인원 수, 사람마다 아바타·이름·역할(비활성이면 "비활성"). **비활성인 사람은 목록 맨 아래에 모인다**(나머지 순서는 그대로. 켜고 끄는 즉시 옮겨진다. D-173, 사용자 지정 2026-10-22). 처음에는 나 자신이 골라져 있다. 오른쪽: 이름과 이메일, **계정 정보**(아이디, 이메일, 로그인 방식, 마지막 로그인, 추가된 날), **권한**(워크스페이스 역할), **프로젝트 권한**(프로젝트마다 고르는 목록. 예전에는 대화상자였다), **계정 관리**(비밀번호 재설정, 비활성화. 각각 무슨 일이 일어나는지 한 줄 설명과 버튼). 이 화면만 관리자 설정의 다른 탭보다 넓다(`data-wide`). 좁은 화면에서는 목록이 위, 설정이 아래로 쌓인다.

아직 없는 것: 구성원이 **자기 비밀번호를 바꾸는 기능**. 임시 비밀번호를 받은 사람이 바꿀 방법이 지금은 관리자에게 재설정을 부탁하는 것뿐이다. 다음에 가장 먼저 채울 빈 곳이다.

### 프로젝트

- 만들 때 받는 것: 이름(1~80자), 키, 설명(선택, 500자 이하).
- 키: 영문 대문자로 시작하는 영문 대문자·숫자 2~10자(`FLOW`, `APP2`). 워크스페이스 안에서 유일하고, **만든 뒤에는 바꿀 수 없다**(티켓 번호와 링크가 여기에 묶인다). 화면은 이름에서 키를 제안한다.
- 만든 사람이 관리 역할의 첫 구성원이 된다.
- 프로젝트 삭제는 아직 없다. 보관은 "아카이브"로 생겼다(D-115, 아래 API 표와 화면 표).

### API

공통 규칙은 [../06-api-conventions.md](../06-api-conventions.md).

| 메서드와 경로 | 설명 | 권한 |
|---|---|---|
| `GET /api/v1/users` | 활성 구성원 목록(id, 아이디, 이름, 사진). 사람을 고르는 화면용 | 로그인 |
| `GET /api/v1/admin/members` | 모든 구성원(비활성 포함)과 역할·상태·마지막 로그인 | 관리자 |
| `POST /api/v1/admin/members` | `{ loginId, password, displayName?, role }` → 201 | 관리자 |
| `PATCH /api/v1/admin/members/{id}` | `{ role?, status? }` | 관리자 |
| `PUT /api/v1/admin/members/{id}/password` | `{ password }` → 204 | 관리자 |
| `GET /api/v1/projects` | 쓰는 중인 모든 프로젝트. 들어갈 수 없는 것은 `myRole: null`. 속성과 함께 `health`, `healthUpdatedAt`(최근 업데이트), `issueCount`(취소 제외), `doneCount`, `archivedAt`(여기서는 늘 null)이 온다. **`?archived=true` 면 아카이브된 프로젝트만**(`archivedAt` 이 있다. 누구나 전부 보고, `myRole` 이 `MANAGER` 인 사람이 복원할 수 있다) | 로그인 |
| `POST /api/v1/projects` | `{ name, description?, openToAll? }` → 201 | 로그인 |
| `GET /api/v1/projects/{id}` | 프로젝트와 내 역할 | 프로젝트 구성원 |
| `PATCH /api/v1/projects/{id}` | `{ name?, description?, openToAll? }` (속성은 위 "프로젝트 속성"). `name`·`openToAll` 은 관리 역할만(D-192) | 관리 (속성은 편집) |
| `PUT /api/v1/projects/{id}/icon` | multipart `file` 하나. 256px 정사각 WebP 로 바꿔 저장(M2a 의 변환·저장). 응답은 프로젝트(`iconUrl`) | 관리 |
| `DELETE /api/v1/projects/{id}/icon` | 기본 아이콘으로 되돌림 | 관리 |
| `POST /api/v1/projects/{id}/archive` | 아카이브 → 204. 지우는 것은 없다. 그 뒤로 프로젝트는 목록·사이드바에서 빠지고, 그 프로젝트의 티켓은 티켓 목록에서 빠지며, 프로젝트와 그 아래 주소는 모두 404 `PROJECT_NOT_FOUND` 다(이미 아카이브된 것을 다시 아카이브해도 404). 감사 로그 `PROJECT_ARCHIVED` | 관리 |
| `POST /api/v1/projects/{id}/restore` | 복원 → 프로젝트. 아카이브 전 그대로 돌아온다. 아카이브되지 않은 프로젝트면 404. 감사 로그 `PROJECT_RESTORED` | 관리 (구성원이 아니면 워크스페이스 관리자) |
| `GET /api/v1/projects/{id}/members` | 프로젝트 구성원과 역할. 열린 프로젝트(D-192)면 활성 구성원 전체(`direct` 가 거짓이면 직접 추가되지 않은 사람, 역할은 편집) | 프로젝트 구성원 |
| `PUT /api/v1/projects/{id}/members/{userId}` | `{ role }`. 없으면 추가, 있으면 역할 변경 | 관리 |
| `DELETE /api/v1/projects/{id}/members/{userId}` | 내보내기 → 204 | 관리 |

오류 코드: 404 `PROJECT_NOT_FOUND`, 404 `MEMBER_NOT_FOUND`, 403 `FORBIDDEN`, 409 `LOGIN_ID_TAKEN`, 409 `LAST_MANAGER`, 409 `CANNOT_CHANGE_SELF`, 422 `VALIDATION_FAILED`.

### 화면

| 경로 | 내용 |
|---|---|
| 사이드바 "프로젝트" | 내가 들어갈 수 있는 프로젝트 목록, `+` 로 새 프로젝트 |
| `/` (전체 프로젝트) | Linear 의 프로젝트 목록처럼 표로 보인다 (D-046): 이름, 건강도(D-048), 우선순위, 리드, 목표일, 티켓 수(취소 제외), 상태 아이콘 + 진행률(완료 ÷ 취소 제외 티켓). 줄 전체가 링크. 좁은 화면에서는 이름과 상태만. 머리 오른쪽에 "새 프로젝트" |
| `/project/{id}` | 프로젝트 머리(이름, 설명). 티켓 목록 자리에는 아직 빈 상태 안내 |
| `/project/{id}/settings` | 프로젝트 아이콘 올리기·지우기, 이름 고치기, 구성원 추가·역할 변경·제거, 맨 아래 **"프로젝트 아카이브"**(한 번 더 눌러 확인. 끝나면 `/archived` 로 간다) (관리 역할만). 아이콘은 사이드바, 전체 프로젝트 표, 경로 표시, 개요 머리에 보인다. 없으면 기본 상자 아이콘 |
| `/archived` (아카이브됨, D-115) | 전체 프로젝트 화면의 두 번째 탭. 아카이브된 프로젝트가 같은 표에 **회색으로** 나온다. 줄은 링크가 아니다(들어갈 수 없다). 관리 역할에게는 줄 끝에 "복원" 버튼이 있고, 누르면 줄이 사라지고 전체 프로젝트와 사이드바에 돌아온다. 없으면 빈 상태 안내 |
| `/admin/members` | 워크스페이스 구성원 목록, 추가, 역할 변경, 비활성화, 비밀번호 재설정 (관리자만) |

### 인수 기준 (1단계)

백엔드 통합 테스트(`MembersIntegrationTest`, `ProjectsIntegrationTest`)가 있다.

- [x] 관리자가 만든 구성원이 그 아이디와 비밀번호로 로그인할 수 있다
- [x] 같은 아이디로는 만들 수 없다. 아이디·비밀번호 규칙을 어기면 필드별 오류
- [x] 구성원은 구성원 관리 API 를 쓸 수 없다 (403)
- [x] 비활성화하면 로그인도, 기존 세션도 쓸 수 없다. 다시 활성화하면 로그인된다
- [x] 비밀번호를 재설정하면 새 비밀번호로만 로그인되고 기존 세션은 끝난다
- [x] 관리자는 자기 역할을 바꾸거나 자신을 비활성화할 수 없다
- [x] 프로젝트를 만들면 만든 사람이 관리 역할이 된다. 키가 겹치거나 형식이 틀리면 거부
- [x] 프로젝트 구성원이 아닌 사람은 목록에서 볼 수 있지만(`myRole: null`) 들어갈 수 없고(404), `/access` 로 관리자를 안내받는다 (D-047 로 바뀜)

- [x] 보기·편집 역할은 프로젝트 설정과 구성원을 바꿀 수 없다 (403)
- [x] 마지막 관리 역할은 내보내거나 낮출 수 없다
- [x] 비활성 구성원이나 없는 사람은 프로젝트에 추가할 수 없다
- [x] 비활성화된 구성원은 프로젝트 구성원 목록에 나오지 않고 다시 활성화하면 돌아온다. 비활성 관리 역할은 "마지막 관리 역할"을 셀 때 세지 않는다 (`ProjectsIntegrationTest`, 돌리지 않음. D-173)

화면은 자동 테스트가 없고 에이전트가 브라우저로 확인하지 못했다(lint, typecheck 만 통과).

## 2단계: 프리셋과 티켓 쓰기 (명세만)

### 티켓의 두 부분

**속성** (모든 티켓이 같다. 목록에서 거르고 정렬하는 데 쓴다)

| 속성 | 값 |
|---|---|
| 상태 | 프로젝트의 상태 목록 중 하나 |
| 프리셋 | 버그 / 고도화 / 기능 요청. 만든 뒤에도 바꿀 수 있다(문서는 그대로 둔다) |
| 담당자 | 프로젝트 구성원 여러 명(최대 10명) 또는 없음 (D-125) |
| 우선순위 | 없음 / 긴급 / 높음 / 보통 / 낮음 |
| 기한 | 날짜 또는 없음 |
| 라벨 | 프로젝트의 라벨 여러 개 |

프리셋마다 입력 칸을 따로 두지 않는다. 그렇게 하면 Jira의 필드 설정이 된다 (D-033).

**문서** (Outline 같은 부분)

- 제목(티켓 제목) + 본문. 본문은 블록 편집기: 제목 1~3단계, 문단, 목록, **체크리스트**, 코드 블록, 인용, 표, 구분선, 이미지, 링크.
- 본문의 제목들로 **목차**가 자동으로 만들어져 오른쪽에 보이고, 누르면 그 위치로 간다.
- `/` 로 블록 삽입, 마크다운 입력(`## `, `- `, `[] `)이 바로 서식으로 바뀐다.
- 이미지는 붙여넣거나 끌어다 놓으면 올라간다. M2a 의 변환·저장을 그대로 쓴다(본문 이미지는 최대 1600px).
- 저장 버튼이 없다. 멈추면 자동 저장하고 "저장됨"을 보여준다.

### 프리셋

새 티켓을 만들 때 프리셋을 고르면 본문에 목차가 깔린다. 각 제목 아래에는 무엇을 쓰면 되는지 안내 문구가 흐리게 보이고, 쓰기 시작하면 사라진다.

| 프리셋 | 깔리는 목차 |
|---|---|
| 버그 | 무슨 문제인가 / 재현 방법 / 기대한 결과 / 실제 결과 / 환경 / 완료 조건 |
| 고도화 | 배경 / 현재 동작 / 바꾸려는 동작 / 영향 범위 / 완료 조건 |
| 기능 요청 | 왜 필요한가 / 누가 쓰는가 / 원하는 동작 / 범위 밖 / 완료 조건 |

- 모든 프리셋의 마지막은 **완료 조건**이고 체크리스트로 시작한다. 본문의 체크박스 수가 목록에서 진행률(`3/5`)로 보인다. 개발자가 "무엇이 되면 끝인가"를 여기서 본다.
- 프로젝트 관리 역할은 프리셋의 목차 제목과 안내 문구를 고칠 수 있다. 프리셋을 새로 만들거나 지우는 것은 없다 (사용자 확정).
- 프리셋을 고쳐도 이미 쓴 티켓은 바뀌지 않는다.

### 개발자가 쓰는 것

- **티켓 키** `FLOW-12`: 누르면 복사. 브랜치 이름과 커밋 메시지에 쓴다.
- **"준비됨" 상태**: 기획이 끝나 개발을 시작해도 되는 티켓. "백로그"는 아직 쓰는 중이라는 뜻이다.
- **완료 조건 진행률**: 목록과 상세에 보인다.
- **변경 이력** (4단계): 준비됨 이후에 본문이 바뀌면 무엇이 바뀌었는지 보인다.

### 상태 목록 (프로젝트를 만들 때 기본으로 생긴다)

| 상태 | 범주 | 뜻 |
|---|---|---|
| 백로그 | backlog | 쓰는 중이거나 아직 다듬지 않음 |
| 준비됨 | unstarted | 내용이 정리되어 개발을 시작할 수 있음 |
| 진행 중 | started | 개발 중 |
| 완료 | completed | 끝남 |
| 취소 | canceled | 하지 않기로 함 |

범주 5개는 고정이고, 범주 안에서 상태를 추가하거나 이름을 바꾸는 것은 이후에 다룬다.

### 편집기와 저장 (기술 결정, D-034)

- 편집기: **Tiptap**(ProseMirror 기반). 직접 만들지 않는다.
- 저장 형식: 편집기의 문서 JSON 을 `jsonb` 로 저장한다. 검색과 미리 보기를 위해 서버가 본문에서 뽑은 평문을 함께 저장한다.
- 서버는 받은 문서를 허용된 블록 종류만 남기도록 검증한다. HTML 을 저장하거나 그대로 내보내지 않는다.
- **동시 편집**: 한 글자씩 합쳐지는 공동 편집은 하지 않는다. 티켓마다 `version` 을 두고, 저장할 때 내가 본 버전을 함께 보낸다. 그 사이 다른 사람이 본문을 고쳤으면 409 로 거절하고, 화면은 "다른 사람이 먼저 고쳤습니다"와 함께 두 내용을 보여 주고 고르게 한다. 속성(상태, 담당자 등)은 필드 단위로 나중 값이 이긴다.
- 같은 티켓을 보고 있는 사람은 아바타로 보여 준다(누가 고치는 중인지 알 수 있게).

## 3단계: 티켓 목록 (명세만)

- `/project/{id}`: 상태별로 묶인 티켓 목록. 한 줄 = 우선순위 · 키 · 프리셋 · 제목 · 완료 조건 진행률 · 라벨 · 기한 · 담당자.
- 필터: 상태, 프리셋, 담당자, 라벨, 우선순위. "내 티켓" 바로 가기. 기한 필터(기한 설정 안 됨 · 기한 지남 · 오늘 마감 · 7일 안에 마감, `?due=none|overdue|today|week`)는 D-223.
- 줄의 상태·담당자·우선순위 아이콘을 눌러 그 자리에서 바꾼다. 즉시 반영하고 실패하면 되돌린다.
- 다른 사람이 바꾼 것은 WebSocket 으로 바로 반영된다 ([../02-architecture.md](../02-architecture.md) "실시간 동기화").
- 화면의 세부는 [../01-product.md](../01-product.md) 4.2 를 따른다.

## 4단계: 댓글과 변경 이력 (처음 쓴 명세. 구현된 모습은 "지금 구현된 범위"의 댓글·`@` 태그·티켓 활동)

- 댓글: 티켓 아래에 시간순. 본문과 같은 편집기의 가벼운 판(제목 없음). `@` 로 구성원 언급.
- 변경 이력: 속성 변경은 "김지민이 상태를 준비됨 → 진행 중으로 바꿨습니다"처럼 한 줄로, 댓글 사이에 시간순으로 섞여 보인다. 본문 변경은 "본문을 고쳤습니다"와 함께 이전 판을 볼 수 있다(이전 판 보기는 지금은 만들지 않기로 했다, D-225).

### 상위 티켓 바로 이동 (2026-10-28, 확정)

티켓 상세 옆 패널의 **상위 티켓 번호·제목을 누르면 해당 상위 티켓으로 이동**한다. 편집 역할에게는 옆에 연필 모양의 **상위 티켓 변경** 버튼을 별도로 두고, 기존 검색·선택·해제 동작은 이 버튼에서 제공한다. 상위 티켓이 없으면 기존처럼 상위 티켓 고르기를 표시한다. 읽기 역할도 상위 티켓으로 이동할 수 있다. API·저장 데이터는 바꾸지 않는다.

### 티켓 직접 열기의 시스템 뒤로가기 (2026-10-28)

주소·알림으로 티켓을 직접 열었거나 새로고침한 창도 시스템 뒤로가기로 전체 티켓 목록으로 닫는다. 직접 연 창에만 같은 주소의 이력 항목을 만들어 뒤로가기를 처리한다. 목록에서 연 티켓 및 티켓 사이 이동은 기존 Next.js 이력으로 돌아간다. 창의 닫기 버튼도 같은 경로를 사용한다.

### 폴더블의 상세 배치 (2026-10-28)

펼친 폴드에서는 PC처럼 본문 왼쪽·속성 오른쪽 두 단으로 표시한다. 상세 컨테이너 560px부터 두 단이며 접힌 좁은 화면은 한 단이다. 중간 폭에서도 창의 여백을 제외한 너비를 활용한다.
