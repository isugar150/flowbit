# 관리자: 파일 관리

상태: **구현됨** (2026-10-22). 사용자 요청: ① 삭제한 티켓·문서·댓글을 영구 삭제하는 배치(D-132)가 돌 때 그 안의 사진(WebP 사본과 원본)도 함께 정리 ② 커밋 전에 파일을 지우는 순서 고치기 ③ 저장소와 DB 를 맞춰 보는 정리를 **관리자 페이지**로, 파일 관리에 대한 모든 항목(통계 포함)을 보이게. 결정은 D-171, D-172.

## 범위

- 관리자 설정의 **"파일 관리"** 탭(`/admin/files`): 저장소 정보, 통계, 정합성 점검, 정리
- 보관 배치(D-132)가 영구 삭제를 한 뒤 **쓰는 곳이 없어진 사진을 지운다**
- 파일을 지우는 것은 **DB 변경이 커밋된 뒤에** 한다 (롤백되면 파일은 그대로)

범위 밖: 파일 올리기·내려받기·크기 제한(M2a, M3), 로컬 파일을 S3 로 옮기는 도구, 파일 이름이나 종류로 찾기, 파일 한 개씩 지우기, 백업 파일에 파일 넣기.

## 파일의 종류

새로 올리는 파일은 올린 날짜 폴더(`yyyy/MM/dd`, UTC) 안에 쌓이고, 예전 파일은 영역 폴더 바로 아래에 있다(D-182). 점검은 둘 다 훑고 키(마지막 이름)로 비교한다.

저장소(로컬 폴더 또는 S3, D-167)에는 세 영역이 있다.

| 영역 | 폴더 | 무엇 | 누가 가리키나 |
|---|---|---|---|
| 첨부 | `files/<uuid>` (D-182 이후는 `files/2026/10/22/<uuid>`) | 티켓 첨부, 티켓 댓글 파일, 문서·프로젝트·목표 댓글 파일, 편집기 본문의 파일 블록. 올린 그대로 | `issue_attachments.file_key`, `content_files.file_key`, 본문(`content` jsonb)의 `/api/v1/editor-files/<uuid>` |
| 사진 | `images/<uuid>.webp` | 프로필 사진, 로고, 프로젝트 아이콘, 편집기·댓글에 넣은 사진의 WebP 사본 | `users.avatar_key`, `instance_settings.logo_key`, `projects.icon_key`, 본문(`content` jsonb)의 `/api/v1/files/<uuid>.webp` |
| 원본 | `originals/<uuid>` | 사진을 올린 그대로(D-169). 사본의 키에서 `.webp` 를 뺀 이름 | 사본이 쓰이는 동안 |

## "쓰는 곳이 없다"는 것: 고아 파일

- **첨부 영역**: 어느 표의 `file_key` 열에도 없는 키.
- **사진 영역**: 어떤 표의 어떤 글 열(`text`·`varchar`·`json`·`jsonb`)에도 `<uuid>.webp` 모양의 글자가 없는 키. 열을 하나하나 고르지 않고 **데이터베이스의 모든 글 열을 훑는다**(`information_schema` 로 열 목록을 얻는다). 그래서 사진이 들어갈 수 있는 표가 늘어도 빠뜨리지 않는다. 훑지 않는 것은 감사 기록(`audit_events`)과 Flyway 기록뿐이다.
- **원본 영역**: 사본(`<uuid>.webp`)이 쓰이지 않는 키.
- 삭제만 표시된 티켓·문서·댓글(보관 기간 안, D-132)은 아직 행이 있으므로 그 안의 사진은 **쓰는 곳이 있는 것**이다. 복원하면 사진도 그대로 보인다. 영구 삭제로 행이 사라져야 고아가 된다.
- **이름이 우리 규칙(uuid)과 다른 파일**은 고아로 보지 않고 "알 수 없는 파일"로 세기만 한다. 지우지 않는다(버킷 접두어를 다른 것과 같이 쓰는 경우를 지키려는 것).
- **유예 24시간**: 저장소에 올라온 지 24시간이 안 된 고아는 지우지 않는다. 사진은 올린 뒤 본문이 저장되기까지, 첨부는 DB 에 적히기까지 잠깐 "쓰는 곳이 없는" 상태이기 때문이다. 나이는 저장소가 아는 수정 시각(로컬은 파일 수정 시각, S3 는 `LastModified`)으로 잰다.

## 화면 (`/admin/files`)

위에서부터 한 페이지에 보인다. 데이터는 열 때마다 새로 읽고(저장소 목록 + DB 훑기라 파일이 많으면 몇 초 걸린다), "다시 점검" 버튼으로 다시 읽는다.

1. **저장소**: 종류(로컬 폴더 / Amazon S3), 위치(폴더 경로, 또는 버킷과 접두어·리전·엔드포인트), 점검 시각. 접근 키는 보이지 않는다.
2. **전체**: 파일 수와 용량(세 영역의 합). 영역별(첨부·사진 사본·원본)로도 수와 용량.
3. **종류별**: 티켓 첨부 / 티켓 댓글 파일 / 문서·프로젝트·목표 댓글 파일 / 보내지 않은 파일(올리고 댓글을 안 보낸 것) / 프로필 사진 / 워크스페이스 로고 / 프로젝트 아이콘 / 본문·댓글의 사진 — 각각 수와 용량(사진은 사본+원본). 그리고 **보관 중인 삭제분**: 삭제 표시된 티켓·문서·댓글에 붙은 첨부 파일(데이터 보관 기간이 지나면 지워진다. 링크: 데이터 보관 설정).
4. **올린 사람별**: 용량이 큰 순서 5명(이름, 파일 수, 용량).
5. **큰 파일**: 용량이 큰 첨부 10개(파일 이름, 용량, 올린 사람, 어디에 붙었는지(티켓 키로 열림, 또는 "문서·프로젝트·목표 댓글"), 올린 날).
6. **정합성 점검**: 
   - 정리할 수 있는 고아 파일(수·용량, 영역별)과 유예 중인 것의 수. 목록 일부(20개: 영역, 키, 용량, 수정 시각, 지금 지울 수 있는지).
   - 누락된 파일: DB 는 아는데 저장소에 없는 것(수, 목록 20개: 파일 이름·키·위치). 이 파일은 열 수 없다.
   - 원본이 없는 사진: D-169 이전에 올려서 원본이 없는 것의 수(알림만).
   - 알 수 없는 파일의 수(알림만).
   - **"고아 파일 정리"** 버튼: 정리할 수 있는 것이 있을 때만 켜지고, 한 번 더 눌러 확인한다. 끝나면 지운 수·용량·실패 수를 보여 주고 다시 점검한다.

## API

| 메서드 | 경로 | 권한 | 설명 |
|---|---|---|---|
| GET | `/api/v1/admin/files` | 관리자 | 위 화면의 모든 값(아래 모양). 저장소를 읽을 수 없으면 503 `STORAGE_UNAVAILABLE` |
| POST | `/api/v1/admin/files/cleanup` | 관리자 | 지금 지울 수 있는 고아 파일을 지운다. `{ deleted: { files, images, originals }, bytes, failed }`. 감사 기록 `FILES_CLEANED` |

```
{
  checkedAt, storage: { type: "LOCAL" | "S3", location, region, endpoint },
  areas: { files, images, originals, total }, total,          // 각각 { count, bytes } (영역을 묶은 값에는 세 영역의 합 `total` 도 있다)
  uses: { ticketAttachments, ticketCommentFiles, contentCommentFiles, pendingFiles,
          avatars, logo, projectIcons, contentImages, awaitingPurge },   // 각각 { count, bytes }
  topUploaders: [{ userId, name, count, bytes }],
  largestFiles: [{ name, bytes, uploader, source, issueKey, createdAt }],  // source: TICKET_ATTACHMENT | TICKET_COMMENT | CONTENT_COMMENT
  consistency: {
    graceHours, orphans: { files, images, originals }, cleanable, inGrace,   // { count, bytes } / inGrace 는 수
    orphanSamples: [{ area, key, bytes, modifiedAt, cleanable }],
    missing: { files, images }, missingSamples: [{ kind, name, key, source, issueKey }],   // kind: FILE | IMAGE
    imagesWithoutOriginal, unknownObjects
  }
}
```

## 보관 배치와의 연결 (D-171)

`RetentionService.purge()` 가 한 번 돌 때 지운 것이 있으면(영구 삭제한 티켓·문서·댓글, 보내지 않고 하루가 지난 파일) **행을 지우고 첨부 파일을 저장소에서 지운 다음**, 위의 정의대로 고아를 찾아 **유예 24시간이 지난 것을 지운다**(사진 사본과 원본 모두). 지운 것이 있으면 감사 기록 `FILES_CLEANED`(행위자 없음). 이렇게 영구 삭제의 시점(관리자 설정의 데이터 보관 기간)을 그대로 따라간다: 기간을 "영구 삭제 안 함"으로 둔 것은 행이 남으므로 사진도 남는다.

- 지운 것이 없는 배치는 저장소를 읽지 않는다(매시간 목록을 읽지 않게).
- 안전 장치: 저장소에 사진이 20개 이상인데 DB 가 쓰는 사진이 하나도 없으면 **자동 정리를 하지 않고** 경고만 남긴다(훑기에 문제가 있다는 뜻일 수 있다). 관리자 화면의 정리는 목록을 보고 직접 누르는 것이라 이 검사를 하지 않는다.
- 저장소를 읽다 실패하면 아무것도 지우지 않는다.

## 파일 삭제는 커밋 뒤에 (D-172)

댓글 수정(빠진 파일), 첨부 삭제, 보내지 않은 파일 되돌리기는 DB 변경을 `@Transactional` 안에서 하는데, 예전에는 저장소의 파일을 그 안에서(커밋 전에) 지웠다. 뒤에서 오류가 나 롤백되면 DB 는 파일을 가리키는데 파일은 없는 상태가 된다. 이제 `AfterCommit.run { … }` 으로 **커밋에 성공한 뒤에** 지운다(`common/transaction/AfterCommit.kt`, Spring 의 `TransactionSynchronization.afterCommit`). 트랜잭션 밖에서 부르면 바로 실행한다. 커밋 뒤 삭제가 실패하거나 서버가 그사이 멈춰도 행은 이미 없으므로 파일은 고아가 되어 위의 정리가 회수한다.

반대쪽(올린 파일은 있는데 그 요청이 롤백된 경우)도 고아 정리가 회수한다.

## 인수 기준 (`AdminFilesIntegrationTest`, `RetentionIntegrationTest`, `AfterCommitTest`)

- 관리자만 보고(403), 올린 첨부·프로필 사진이 영역별 수와 용량, 종류별에 반영된다
- DB 가 모르는 파일은 고아로 세고, 24시간이 안 지났으면 유예 중, 지나면 정리하면 지워진다. 쓰는 사진·첨부는 지워지지 않는다
- DB 는 아는데 저장소에 없는 첨부는 누락으로 센다
- 본문에 넣은 사진은 티켓을 삭제만 했을 때는 남고, 영구 삭제 배치 뒤에는 사본과 원본이 모두 지워진다. 다른 본문에도 들어 있는 사진은 남는다
- 커밋 뒤 삭제: 롤백된 트랜잭션에서는 파일을 지우지 않고, 커밋되면 지운다

## 확인이 필요한 것

- 화면과 실제 S3 로는 아무도 확인하지 않았다(Docker 가 없어 통합 테스트도 돌리지 못했다).
- 저장소 목록을 통째로 메모리에 올린다. 파일이 수십만 개를 넘는 설치에서는 느리거나 메모리를 많이 쓴다.
- 감사 기록(`audit_events`)을 훑지 않는다. 거기에 사진 주소가 들어가는 일이 생기면 정리가 그 사진을 지운다.
- 고아 정리를 배치가 매번 하지는 않는다(지운 것이 있을 때만). 올리고 저장하지 않은 사진만 쌓이는 경우는 관리자가 화면에서 정리한다. 매일 자동으로 돌릴지.
- 삭제 표시된 것에 붙은 사진(첨부가 아닌)의 용량은 "보관 중인 삭제분"에 넣지 않았다(어느 행에 쓰이는지 따로 훑어야 한다).
