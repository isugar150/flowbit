# 04. 프론트엔드 가이드 (Next.js + shadcn/ui)

UI 작업을 시작하기 전에 [07-skills-guide.md](07-skills-guide.md) 의 "프론트엔드" 항목에서 해당 스킬을 읽는다. 특히 shadcn 컴포넌트를 다룰 때는 `agent-skills/shadcn-ui-ui/skills/shadcn/SKILL.md` 를 먼저 본다.

## 폴더 구조

```
frontend/
├─ src/
│  ├─ app/
│  │  ├─ (public)/           로그인 없이 보는 화면
│  │  │  ├─ setup/           초기 설정 마법사
│  │  │  └─ login/
│  │  ├─ (app)/              로그인 후 화면 (공통 레이아웃: 사이드바, 헤더)
│  │  ├─ layout.tsx
│  │  └─ globals.css         Tailwind, 디자인 토큰
│  ├─ components/
│  │  ├─ ui/                 shadcn CLI 가 생성한 컴포넌트 (직접 만든 파일을 두지 않는다)
│  │  └─ <기능>/             여러 화면에서 쓰는 조합 컴포넌트
│  ├─ features/<기능>/       기능별 코드: api.ts, schema.ts, 컴포넌트, 훅
│  ├─ lib/                   API 클라이언트, 유틸
│  └─ messages/              UI 문자열 (ko, en)
├─ e2e/                      Playwright 테스트
└─ proxy.ts                  인증 상태에 따른 리다이렉트 (Next.js 16 의 proxy 규칙)
```

한 화면에서만 쓰는 컴포넌트는 그 라우트 폴더 안에 `_components/` 로 둔다.

## 서버 컴포넌트와 클라이언트 컴포넌트

- 기본은 서버 컴포넌트다. 상태, 이벤트 핸들러, 브라우저 API 가 필요한 부분만 `"use client"` 로 분리하고, 그 범위를 가능한 한 작게 유지한다.
- 첫 화면에 필요한 데이터는 서버 컴포넌트에서 가져온다.
- 사용자 조작으로 일어나는 조회/변경은 클라이언트에서 TanStack Query 로 처리한다.
- 폼은 react-hook-form + zod 로 만든다. 검증 스키마는 `features/<기능>/schema.ts` 에 둔다.

## 백엔드 호출

- 브라우저는 항상 같은 출처의 `/api/v1/...` 를 부른다. Next.js 가 백엔드로 넘긴다 ([02-architecture.md](02-architecture.md)).
- 호출은 `lib/api` 의 클라이언트 하나를 거친다. 컴포넌트에서 `fetch` 를 직접 쓰지 않는다. 이 클라이언트가 CSRF 헤더 추가, 오류(Problem Details) 파싱, 401 처리를 맡는다.
- 요청/응답 타입은 백엔드 OpenAPI 문서에서 생성한다. 손으로 중복 정의하지 않는다.
- 서버 오류의 필드별 메시지(`errors[]`)는 해당 폼 필드 아래에 표시한다. 필드와 무관한 오류는 폼 상단이나 토스트로 보여준다.
- 클라이언트 검증은 편의 기능이다. 같은 규칙을 백엔드도 반드시 검증한다.

## shadcn/ui 규칙

- 컴포넌트는 shadcn CLI 로 추가한다. 이미 있는 컴포넌트를 새로 만들지 않는다.
- `components/ui/` 의 파일은 꼭 필요할 때만 고친다. 변형이 필요하면 감싸는 컴포넌트를 만든다.
- 색, 간격, 반경은 디자인 토큰(CSS 변수)으로만 쓴다. 컴포넌트에 임의의 hex 값이나 `w-[373px]` 같은 값을 넣지 않는다.
- 아이콘은 shadcn 프리셋이 정한 아이콘 세트 하나만 쓴다.

## 디자인 원칙

Flowbit은 하루 종일 쓰는 업무 도구다. 꾸밈보다 밀도, 속도, 예측 가능성이 중요하다.

- **기본값처럼 보이는 UI를 피한다.** 색, 글꼴, 간격은 의도를 가지고 정하고 `globals.css` 의 토큰으로 관리한다. 의미 없는 그라데이션, 과한 둥근 모서리, 장식용 애니메이션을 쓰지 않는다.
- **모든 상태를 만든다.** 로딩, 빈 상태, 오류, 비활성, 긴 텍스트, 데이터가 아주 많을 때. 화면 하나를 끝냈다고 말하려면 이 상태들이 모두 구현되어 있어야 한다.
- **애니메이션은 목적이 있을 때만.** 자주 반복되는 동작(목록 이동, 키보드 조작)은 애니메이션 없이 즉시 반응한다. 쓰는 경우 `transform`/`opacity` 만 움직이고 `prefers-reduced-motion` 을 따른다.
- **문구는 구체적으로.** 버튼은 동작을 말한다("저장", "관리자 계정 만들기"). 오류는 무엇이 잘못됐고 어떻게 고치는지 말한다.
- **키보드 우선.** 모든 기능을 키보드로 쓸 수 있고, 포커스 표시가 항상 보인다.
- 라이트/다크 테마를 처음부터 함께 만든다.

## 접근성

- WCAG 2.2 AA 를 기준으로 한다.
- 폼 필드에는 항상 연결된 레이블이 있다. 오류 메시지는 `aria-describedby` 로 필드와 연결하고, 제출 실패 시 첫 오류 필드로 포커스를 옮긴다.
- 색만으로 정보를 전달하지 않는다.
- 터치 대상은 최소 24×24px.

## 다국어

UI 문자열을 컴포넌트에 직접 쓰지 않고 `messages/` 에서 가져온다. 기본 언어는 한국어다. (초안 — 라이브러리 선택은 [09-decisions.md](09-decisions.md) 미결정 항목)

## 테스트

| 종류 | 대상 | 도구 |
|---|---|---|
| 단위/컴포넌트 | 검증 스키마, 유틸, 로직이 있는 컴포넌트 | Vitest, Testing Library |
| E2E | 기능 명세의 주요 사용자 흐름 | Playwright |

- 기능 명세의 사용자 흐름마다 E2E 테스트가 하나 이상 있어야 한다.
- 작업을 끝내기 전에 `pnpm lint`, `pnpm typecheck`, `pnpm test` 가 통과해야 한다.
- UI 를 바꿨으면 실제 브라우저에서 라이트/다크, 좁은 폭을 직접 확인한다.

## 화면 완료 전 점검

1. 디자인 리뷰 스킬로 점검한다 ([07-skills-guide.md](07-skills-guide.md) 의 "리뷰" 항목).
2. 극단적인 데이터(아주 긴 이름, 빈 값, 이모지, 한글/영문 혼합)로 깨지지 않는지 확인한다.
3. 키보드만으로 흐름 전체를 끝까지 진행해 본다.
